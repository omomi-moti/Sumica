## Phase 1: 2D版

### 完成の定義

以下6つが満たせていれば成功。**これ以外は全部おまけ。**

1. 初回起動でオンボーディングが動き、自分の部屋が組み上がる
2. 部屋が時間経過で汚れ、操作するとモップで磨くように綺麗になる
3. 朝8時に通知が来て、タップすると確認ができる
4. アプリを閉じて翌日開いても状態が正しい
5. 実機に入っていて、自分が使える
6. 画面収録が撮れている

作業中に何か思いついたら、この6つのどれかを助けるかで判断する。

### 作業単位

日付を割り当てず、順序だけ決めておく。まとまった時間が取れたときに上から進める。

| # | 内容 |
|---|---|
| 1 | Domain（汚れ計算 + テスト）、SwiftData、`Canvas` で部屋が出る |
| 2 | 部屋の描画を詰める（長方形の配置、色の補間、粒子） |
| 3 | **モップのアニメーション。** 確認の操作方法（[spec.md](spec.md) §2.3）もここで決める |
| 4 | 通知（スケジュール + 許可 + 確認導線）、実機確認 |
| 5 | オンボーディング2画面 + 遷移演出 |
| 6 | 配色・余白・タイポグラフィ、通知文面 |

**3 が本丸。** ここが最も重く、他を削ってでも時間を割く。

**5 を後ろに置いた理由。** 部屋と通知が動いていればアプリとして成立するため、時間切れ時に切り捨てられる位置に置く。無くても初期値をハードコードすれば動く。

**4 を最後にしない。** 実機確認が必須なので、最終日に置くと詰む。

## Phase 2: 3D版

### 位置づけ

2Dと3Dは **最終形で共存する**。3D完成後も2Dを残す。

用途が違うため。3Dは没入感があるが、朝の忙しい時に回して確認したくはない。2Dは一瞬で全体が見える。メイン画面に切替ボタンを置いて差し替える。

**維持コストは2倍になる。** 汚れの表現を変えるたび2箇所直すことになる。許容範囲に保つため、共通ロジックを Domain に寄せ、描画層は「関数を受け取って描くだけ」に徹する。

**切替ボタンの置き場所は Phase 1 のうちに確保する。** 実装はしないが、余白調整の工程で「右下にボタンが1つ入る前提」で余白を取っておく。

### 移行で変わるもの

| 項目 | 2D | 3D |
|---|---|---|
| 描画 | `Canvas` | `RealityView` |
| 再描画駆動 | `TimelineView` | RealityKit のレンダリングループ |
| ジオメトリ | 長方形を塗る | `MeshDescriptor`（長方形を対角線で三角形2枚に切る） |
| 汚れ表現 | 色の濁り + 粒子 | `PhysicallyBasedMaterial` の baseColor / roughness |
| 粒子 | `Canvas` に円を描く | Entity を撒く / テクスチャに焼く |
| モップ | `trimmedPath` + クリップ | 同じ経路をテクスチャのマスク生成に使う |
| カメラ | なし | `.realityViewCameraControls(.orbit)` |
| ヒットテスト | 範囲比較 | `SpatialTapGesture` + `targetedToAnyEntity` |

Domain 層・Repository・通知・オンボーディングは**一切変わらない**。だから2D版を完成させることは3Dへの遠回りではなく最短ルートになる。

### 設計メモ

**粒子の3D実装は3案ある。** (A) 小さな Entity を撒く — 直感的で個別に動かせるが、区画あたり数十個が限界。(B) 配置からテクスチャを生成してマテリアルに貼る — 数千個でも平気だが個別の動きは出せない。(C) `ParticleEmitterComponent` — 舞い上がる埃には向くが、床の静的な汚れには制御が面倒。

汚れ度が低いうちは A、増えたら B に切り替えるハイブリッドが有望。ただし最適化の話なので実測してから決める。

**3Dのほうが面白くなる部分。** 粒子に高さを持たせられる（`height` の範囲に撒けば机の上や棚の上に乗る）。モップで撫でた粒が1個ずつ違うタイミングで散る。回すと机の上の汚れが手前に来る——「回せる」ことの価値が一番わかりやすく出る。

**カメラ。** `.orbit` をそのまま使うと視点が迷子になる可能性がある。仰角の制限とズーム範囲の制限を検討し、「どう回しても部屋がちゃんと見える」を保証する。

**アクセシビリティ（2D側の宿題）。** `Canvas` は SwiftUI の View 階層の外にあるため、中身は VoiceOver に乗らない。`accessibilityChildren(children:)` で個別要素を宣言する必要がある。Phase 1 では入れないが、App Store に出すなら必須。

### 進め方

RealityKit の素振り（箱を1つ置いて回すだけの実験プロジェクト）を先に挟む。ECS の考え方に慣れる期間が要る。Phase 1 の残りとどちらを先にするかは、着手できる状況になった時点で判断する。

## 決着済みの設計判断

実装をブロックしていた7件。詳細は各ドキュメントに反映済み。

| | 項目 | 決定 |
|---|---|---|
| 1 | 汚れ曲線 | 半減期モデル。表示クランプ 0.6、通知閾値 0.5 |
| 2 | `dateWhenReaching` の失敗 | `Date` を返す。`assert` + クランプ |
| 3 | 区画の形 | 長方形のみ。頂点配列と扇状分割は不採用 |
| 4 | 座標系 | Domain は正規化のまま。変換は描画層 |
| 5 | `dailyQuestion` の評価時刻 | `startOfDay` |
| 6 | 通知 | 配列で返す。初期 3日分 |
| 7 | `halfLife` 初期値 | 1.5 / 3.5 / 6 / 3.5 / 3.5 日 |
| 8 | Domain が扱う型 | `Room` / `Area` は `Data/Models/` の `@Model`。Domain は値型の `AreaSnapshot` を受け取る |
| 9 | 座標の数値型 | `Double`。表示名は永続化せず `AreaKind` の定数にする |
| 10 | 区画の順序 | `AreaKind.allCases` の宣言順を正とする。`Dictionary` を直接回さない |
| 11 | 設定値の保存先 | `UserDefaults`。SwiftData が持つのは部屋の状態だけ |
| 12 | 表示クランプの適用箇所 | 描画層。`dirtiness()` は生値を返す |
