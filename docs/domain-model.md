# ドメインモデル

`Domain/` に置くデータと純粋関数の定義。実装と同期が必要なので、変更したらこのファイルも直す。

設計の理由は [architecture.md](architecture.md)、プロダクト仕様は [spec.md](spec.md)。

---

## 1. エンティティ

```
Room
├─ id: UUID
├─ layoutType: LayoutType         // 当面 .myRoom のみ
├─ createdAt: Date                // 初回7日間の判定に使う
└─ areas: [Area]

Area
├─ id: UUID
├─ kind: AreaKind
├─ lastVerifiedCleanAt: Date      // 「最後に綺麗だと確認した時刻」
└─ cleanedCount: Int              // 累積。減らない。表示はしない
```

**永続化対象は `Room` と `Area` のみ。** 座標・汚れ速度・タスク文言は定数としてコードに持つ。

表示名も永続化しない。`AreaKind` ごとに固定で、改名する画面が無いため（[spec.md](spec.md) §4.3）。`AreaKind` の定数として持つ。

**設定値はここに含めない。** 通知のオン/オフ・通知時刻・ペースは `UserDefaults` に置く（[architecture.md](architecture.md) §2.3）。SwiftData が持つのは部屋の状態だけ。

### `Room` / `Area` は `Data/` 側に置く

この2つは SwiftData の `@Model` として `Data/Models/` に置く。`Domain/` は SwiftData に依存しないため、**Domain の関数はこれらを受け取らない。**

代わりに `Domain/` に値型のスナップショットを1つ置き、Domain の関数はその配列を受け取る。

```swift
struct AreaSnapshot: Identifiable {
    let id: UUID
    let kind: AreaKind
    let lastVerifiedCleanAt: Date
    let halfLife: TimeInterval   // ペースを掛けた後の実効値
}
```

**`halfLife` は実効値を詰める。** `Tuning` の区画別定数に、ユーザーが設定したペース（0.7 / 1.0 / 1.5）を掛けた後の値。

`kind` から `Tuning` を引けば足りるように見えるが、ペースは `UserDefaults` にあり `Domain/` からは読めない。掛け算を変換プロパティ側で済ませておくことで、Domain の関数は `Tuning` も `UserDefaults` も参照せずに汚れ度を計算できる。

`cleanedCount` は Domain の計算に使わないので持たせない。

変換は `@Model` 側にプロパティを1つ生やして行う。Mapper 層は作らない。

**なぜ `@Model` をそのまま渡さないか。**

| | |
|---|---|
| 依存の向き | 渡すと `Domain` → SwiftData の依存が生まれる。`Data` → `Domain` の一方向に保つ |
| 純粋関数の前提 | `@Model` は `class`。参照型を渡すと関数の実行中に中身が変わりうるため、「同じ入力なら同じ出力」が保証できない。値型のスナップショットなら固定される |

`layoutType` は値が1つしかなくても今から入れる。フィールドを後から追加するとマイグレーションが必要になるのに対し、enum の case を足すのはコストゼロという非対称性を利用する。

**`lastVerifiedCleanAt` という名前について。** 「最後に掃除した時刻」ではなく「最後に綺麗だと確認した時刻」。確認を第一の操作にした（[spec.md](spec.md) §2.2）結果、実際にやっていることはこちら。

## 2. アクション（3種類）

| アクション | 入り口 | 効果 |
|---|---|---|
| 確認（綺麗だった） | 毎日の確認 | `lastVerifiedCleanAt = now` |
| タスク完了 | 確認で「散らかってる」→ タスク実行 | `ratio` で部分的に now 側へ寄せる |
| 区画掃除 | 区画を操作（本気の掃除） | `lastVerifiedCleanAt = now` + `cleanedCount` +1 |

```swift
func partiallyCleaned(lastVerifiedCleanAt: Date, now: Date, ratio: Double) -> Date
```

「今日のタスクを1つやった」と「机まわりを本気で片付けた」は別物なので2段階を維持する。

## 3. ジオメトリ

### 区画は長方形のみ

区画の形は**長方形に限定する**。縦横の範囲2本で保持する。

| 選択肢 | 却下理由 |
|---|---|
| 頂点配列 + 扇状分割 | L字（凹形状）は扇状分割で破綻するため、頂点配列にしても結局作れない。得られるものが無いのに、粒子分布・当たり判定・モップ経路のすべてが三角形分割を経由することになる |

長方形にすることで:

- 粒子の一様分布が乱数2個で出る
- 当たり判定が範囲比較2回
- モップの経路は縦横比を見て長辺方向に往復するだけ
- Phase 2 の `MeshDescriptor` へは、その場で対角線に切って三角形2枚にする

**部屋全体の輪郭は長方形の組み合わせで作る。** §5 の配置では右下が空くため、全体としてはL字型の部屋になる。個々の区画が長方形であれば足りる。

```swift
struct AreaGeometry {
    let x: ClosedRange<Double>  // 正規化座標 0.0-1.0
    let y: ClosedRange<Double>
    let height: Double          // 押し出し高さ。2D描画時は無視
}

struct LayoutDefinition {
    let type: LayoutType
    let geometries: [AreaKind: AreaGeometry]
}

enum LayoutCatalog {
    static let all: [LayoutDefinition] = [.myRoom]
}
```

**区画の順序は `AreaKind.allCases` の宣言順を正とする。** `geometries` は `Dictionary` なので順序を持たない。そのまま回すと実行のたびに並びが変わり、オンボーディングの区画チップの順番が安定しない。**区画を列挙するときは必ず `allCases` を経由する。**

数値型は `Double`。Phase 1 の描画先である `Canvas` が `CGFloat`（実体は `Double`）を扱うため、`Float` にすると描画のたびに変換が入る。Phase 2 で RealityKit に渡すときは `Float` への変換が要るが、それはメッシュ生成の1箇所に閉じる。

### 座標系

**`Domain/` は正規化座標（0.0〜1.0）だけを扱う。** 画面サイズを引数に取らない。

実座標への変換は描画層の責務。`DustDistribution` も `MopPath` も正規化座標で点列を返し、`Canvas` 側が一括変換する。この規約がないと Domain に画面サイズが漏れる。

## 4. 汚れ度の計算

汚れ度は保存せず、`lastVerifiedCleanAt` からの純粋関数として毎回算出する。理由は [architecture.md](architecture.md)。

```swift
/// 0.0（清潔）〜 1.0 に漸近
func dirtiness(lastVerifiedCleanAt: Date, now: Date, halfLife: TimeInterval) -> Double

/// dirtiness が threshold に到達する時刻を逆算
func dateWhenReaching(_ threshold: Double, from: Date, halfLife: TimeInterval) -> Date
```

### 曲線: 半減期モデル

**halfLife ごとに「残っている清潔さ」が半分になる。** 減る量が徐々に小さくなるため、汚れ度の伸びは頭打ちになる。

| 経過（halfLife の何倍か） | 汚れ度 |
|---|---|
| 0 | 0.00 |
| 1倍 | 0.50 |
| 2倍 | 0.75 |
| 3倍 | 0.875 |
| ∞ | 1.00（**到達しない**） |

線形（毎日一定量増える）にしない理由は、放置し始めの数日は目に見えて汚れるのに、1ヶ月放置した部屋が2ヶ月で倍汚くなるわけではない、という実感に合わないため。

### 1.0 は理論上の上限であり、アプリは触らない

汚れ度の使い道は3つで、どれも 1.0 を必要としない。

| 用途 | 必要な範囲 |
|---|---|
| 部屋の色を決める | 0 〜 0.6（表示クランプ） |
| 通知の閾値到達を逆算する | 閾値1点だけ |
| 最も汚れた区画を選ぶ | 大小関係のみ |

**クランプは `dirtiness()` の中で行わない。** 生の値を返し、`Tuning.dirtinessDisplayCap` は描画層が色を決めるときにだけ適用する。

Domain 側で丸めると、放置が長い区画が複数あるときに**全部 0.6 で同着**になり、§6 の「最も汚れている区画を選ぶ」が機能しなくなる。名前のとおり表示用の上限であって、値そのものの上限ではない。

`dateWhenReaching(1.0, ...)` は数学的に答えが存在しない。**閾値に 1.0 以上を渡すことは禁止する。**

### 不正入力の扱い

戻り値は `Date`。`throws` にも Optional にもしない。**失敗時に回復する手段が存在せず、`catch` に書けることがログ出力しかないため。** 呼び出し側を複雑にする見返りがない。

代わりに `assert` + クランプで守る。

| ビルド | 挙動 |
|---|---|
| Debug | 落ちる。開発中に必ず気づく |
| Release | 安全な値に丸めて続行。ユーザーはクラッシュしない |

ガード対象:

| 引数 | 条件 | 理由 |
|---|---|---|
| `threshold` | `< 1.0` | 到達しない値。ただし定数なので実行時に来る経路はほぼ無い |
| `halfLife` | `> 0` | **こちらが本命。** ペース設定（0.7/1.0/1.5倍）が掛かるうえ、将来の自動学習で実行時計算値になる。0 以下だと `NaN` が出て、比較が全て false になり「最も汚れた区画」の選択が黙って壊れる |

## 5. 区画の定義

5区画。メインルーム（6畳）を3分割し、その下に風呂とトイレの正方形を縦に積む。

| 区画 | 想定 | `halfLife` |
|---|---|---|
| 机まわり | 物が積もる場所 | 1.5日 |
| 床 | 掃除機・クイックルワイパー | 3.5日 |
| ベッドまわり | 布団・枕元 | 6日 |
| 風呂 | | 3.5日 |
| トイレ | | 3.5日 |

**`halfLife` はそのまま「通知が飛ぶまでの日数」。** 通知閾値を 0.5 に置いたため、汚れ度が 0.5 に達するのはちょうど halfLife 経過時になる。調整時に換算が要らない。

**物理的な部屋で割らず、掃除の単位で割る。** 「メインルーム」を1区画にするとタップ1回で6畳全体が綺麗になる設計になり、実際の掃除（30分仕事）と乖離する。また机の上と部屋の床では汚れる速さが違うため、同一区画にすると `halfLife` を1つしか設定できず嘘をつくことになる。

```swift
static let myRoom = LayoutDefinition(
    type: .myRoom,
    geometries: [
        .desk:   .init(x: 0...0.571, y: 0...0.129,     height: 0.14),
        .floor:  .init(x: 0...0.571, y: 0.129...0.300, height: 0.01),
        .bed:    .init(x: 0...0.571, y: 0.300...0.429, height: 0.09),
        .bath:   .init(x: 0...0.286, y: 0.429...0.714, height: 0.11),
        .toilet: .init(x: 0...0.286, y: 0.714...1.0,   height: 0.11),
    ]
)
```

全体の縦横比は 0.571 : 1.0 とかなり縦長。iPhone の縦画面には収まりが良いが、下段のテキストと合わせると上下の余白が少なくなる。余白調整時に確認する。

右下に空白ができるが、**そのまま残す**。廊下や玄関として自然に見え、部屋の輪郭が単調な長方形でなくなるぶん絵として面白い。

**未決:** メインルームの3分割を横帯にするか縦割りにするか。机とベッドが実際に左右の壁沿いなら縦割りのほうが自然。座標を差し替えるだけなので、描いてから決める。

### 制約

- 1部屋あたり最大5区画
- 最小タップ領域 44pt 四方以上

## 6. 日々の問い

```swift
/// 同じ日付なら常に同じ結果を返す
func dailyQuestion(areas: [AreaSnapshot], on startOfDay: Date) -> (areaID: UUID, text: String)
```

**「その日の 0:00 時点で最も汚れていた区画」と定義する。**

「最も汚れている区画を選ぶ」と「1日固定する」は、現在時刻で評価する限り両立しない。日中に掃除すれば順位が変わるため。評価時刻を `startOfDay` に固定することで、純粋関数のまま1日を通して同じ結果になる。

引数名が示す通り、渡すのは日付であって時刻ではない。

## 7. 通知の計画

```swift
func plan(areas: [AreaSnapshot], createdAt: Date, from now: Date, days: Int) -> [PlannedNotification]
```

**戻り値は配列。** 1件だけ返す設計だと、アプリを開かない限り次が積まれず通知が止まる（[spec.md](spec.md) §5.1）。

`createdAt` は `Room` のものを別引数で渡す。最初の7日間の判定に使う。

- 積む日数は `Tuning` の定数。初期値 **3**
- 各日の朝8時時点の汚れ度を計算し、閾値 0.5 を超える区画のうち最も汚れているものを選ぶ
- `Room.createdAt` から7日以内は、閾値に関係なく毎日1件入れる。この分岐はこの関数の中で行う
- 1日あたり最大1件

**通知本文は予約時に確定する。** 区画名を含むため、各日の予測状態から文面を生成して埋め込む。

## 8. microTasks

確認で「散らかってる」と答えたときに提示する。区画ごとに3〜4個。ランダムに1つ出すだけなので多くする必要はない。

条件は2つ。**朝1分で終わる**こと、**判断が要らない**こと。後者が重要で、「机を片付ける」は何から手をつけるか考える時点で止まる。対象を1個に指定する。

**「1つ」という言葉を必ず入れる。** 「ゴミを捨てる」と「ゴミを1つ捨てる」では心理的な重さが違う。数を明示すると終わりが見える。

| 区画 | タスク |
|---|---|
| 机まわり | コップを1つ流しに持っていく / 机の上のゴミを1つ捨てる / 出しっぱなしのペンを筆立てに戻す / 充電ケーブルをまとめる |
| 床 | 床の服を1枚拾う / ゴミ箱の袋を替える / 床に置いたカバンを定位置に戻す / クイックルワイパーを1往復かける |
| ベッドまわり | 枕の位置を直す / 布団をめくって空気を通す / 枕元の物を1つどける |
| 風呂 | 排水口の髪を取る / 鏡を1回拭く / シャンプーボトルの底を流す |
| トイレ | 便座を1回拭く / トイレットペーパーを補充する / 床を1回拭く |

**懸念:** 風呂とトイレは朝の動線から外れている可能性がある。朝シャワーの習慣がないと8時に「排水口の髪を取る」は実行されない。運用して外れていると感じたら、水回りを通知対象から外すことを検討する（区画ごとに通知時刻を変えるのは複雑さが増すため採らない）。

## 9. 調整値

運用しながら触る値がコード中に散っていると、調整のたびに探すことになる。1ファイルに集める。

```swift
enum Tuning {
    static let microTaskRatio = 0.4          // タスク完了時に戻る割合
    static let dirtinessDisplayCap = 0.6     // 表示上のクランプ
    static let notificationThreshold = 0.5   // 通知が飛ぶ汚れ度
    static let notificationDays = 3          // 何日分予約するか
    static let defaultPaceMultiplier = 1.0   // 設定の3択は 0.7 / 1.0 / 1.5
    // halfLife の区画別初期値もここ
}
```

**`Tuning` に入るのは定数だけ。** ペースはユーザーが変更する値なので、現在値は `UserDefaults` 側が持つ。`Tuning` が持つのは既定値と選択肢だけ。

**具体値は机上で決めない。** 実際に自分の部屋で1週間動かして感覚が出てから調整する。今やるべきは値を決めることではなく、すぐ変えられる場所に置くこと。
