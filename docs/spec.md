# Sumica — 仕様

部屋を平面図として描き、時間経過で汚れていく様子を可視化する iOS アプリ。

このファイルは **何を作るか** を書く。ドメインモデルは [domain-model.md](domain-model.md)、技術的な決定は [architecture.md](architecture.md)、進め方は [roadmap.md](roadmap.md)。

---

## 1. 背景

### 1.1 課題

掃除の習慣がない。継続できない。

既存の掃除管理アプリ（Tody / Sweepy / おそうじログ / PikaPika / キレイイネ / Tidy / Cleaning Plan）は、調べた限りすべて **タスクのリスト + 汚れゲージ** という形式。開いた瞬間に未完了タスクの一覧が目に入る。継続できていない人間にとって、この画面は責められる体験になる。

またこれらは家族と分担する前提の家庭向けで、単身のワンルームにはオーバースペック。セットアップも重く、始める前に脱落する。

### 1.2 仮説

部屋を **1つの空間** として描き、そこが濁っていく / 澄んでいくを見せると、同じ情報量でも「タスク一覧」ではなく「自分の部屋」として受け取られ、開くことの心理的コストが下がる。

最終的に **回転できる3D** にすることで、この仮説を最も強い形で検証する。平面図はまだ「図面」だが、回せる立体は「空間」になる。

### 1.3 競合調査（2026-08 時点）

- 部屋を絵として描き、そこをタップして掃除する空間UIのアプリは**見つからなかった**
- Tody は「汚れを可視化」と謳うが、実装はエリアごとのカラーバー。空間ではない
- 「Clean Your Room - Step by Step」は写真AIで極小タスクを生成する。タスクを小さく割る発想は共通だが機構が異なる。ただしストリークを主要指標にしており、本アプリの方針とは逆
- 2025年以降、LiDAR で間取りをスキャンする動きがある。業界が「間取りを持つ」方向に向かっている傍証

**説明時の注意:** 「汚れを可視化するアプリ」という言葉のレベルでは Tody と同じ。差分を語るときは「リストではなく間取り図として描いた」まで一息で言う。

### 1.4 名前

**Sumica**（住処）。

掃除をタスクではなく状態として扱う設計にしたため、行為ではなく場所を名前にした。開いた時に見えるのが「タスク」ではなく「自分の部屋」だという設計と一致する。

**既知のリスク（許容する）:** 「Suica」と1文字違いで口頭では誤認されやすい。また「すみか」は住居・暮らし系のサービス名として飽和しており、App Store 検索では埋もれる。リリースしない前提のため Phase 1〜2 では問題としない。Phase 3 で公開する場合は再検討する。

### 1.5 目的

| 目的 | 内容 |
|---|---|
| 実用 | 自分が掃除の習慣をつける |
| 学習 | SwiftUI の描画・アニメーション・空間表現の実装練習 |

学習対象は、`Canvas` の座標計算とテクスチャ表現、`TimelineView` による時間駆動描画、`matchedGeometryEffect` を使った遷移、ローカル通知の設計、そして Phase 2 での RealityKit / ECS。

## 2. 設計方針

1. **責めない。** 継続できない人間が使う前提。罪悪感を与えた時点で負け
2. **開始コストを最小化する。** 初回起動から利用開始まで20秒以内。朝の操作は1分で終わるものだけ
3. **絵で全体を、文字で次の一手を。** 空間表現で失う一覧性をテキストで補う
4. **状態を保存しない。時刻だけ保存する。** [architecture.md](architecture.md) の根幹
5. **綺麗な可能性を常に残す。** §2.2

### 2.1 「責めない」の具体化

| 判断 | 内容 |
|---|---|
| 汚れの上限 | 表示は最大60%。地の色は必ず残す。「荒れてるが、まだ自分の部屋」で止める |
| 連続日数 | **主役にしない。** 1日途切れてゼロに戻る体験は罰になる |
| 累積カウント | **メイン画面に出さない。** 数字が伸びない期間＝サボりが可視化されるため。記録自体はする（`cleanedCount`） |
| 復帰時 | 久しぶりに開いたとき、1区画掃除するだけで見た目が大きく変わる |
| 通知文面 | 主語を部屋側に置く。人を責めない（§5.3） |

### 2.2 「確認」を第一の操作にする

**時間経過は汚れの推定にすぎない。** 掃除していなくても綺麗な日はあるし、掃除した翌日に散らかることもある。実態はユーザーしか知らない。

したがってアプリが提示するのは「これをやれ」ではなく「今どう？」である。

```
確認 → 綺麗だった → 何もしなくていい（汚れリセット）
     → 散らかってた → そこで初めてタスクが出る
```

**この順序が重要。** タスクを先に出す設計だと、綺麗な日にも無駄な指示が出る。確認を先にすると、負荷ゼロの日が正当に発生する。習慣がない人間にとって「今日は何もしなくていい」が起きることは重要。

**「うん」が押しやすすぎる問題は許容する。** 実際は散らかっているのに面倒だから綺麗だと答える、は避けられない。しかし自分専用アプリであり、嘘をついて損をするのは自分だけ。**アプリが嘘を見抜こうとしないほうがいい。**

**確認だけで汚れがリセットされるのは正しい。** 汚れ度は「部屋の状態」を表す値であって「行動量」ではない。掃除回数を数えたいなら `cleanedCount` を別に持てばよい。

**確認の頻度は1日1問。** 最も汚れ度が高い区画1つだけを聞く。全区画聞くと5問になり重くなる。

### 2.3 未決 — 確認をどう「面白く」するか

ただの二択では部屋の絵を作り込んだ意味が薄い。答えが下段のボタンで完結し、上の絵が飾りになってしまう。

**実装しながら決める。** モップのアニメーションを触ってみないと、確認の操作がどうあるべきか判断できない。今決め切ると感触と合わなかったときに縛りになる。

候補:

- **A. 部屋の絵の上で確認する。** 区画を撫でると汚れが晴れる。綺麗なら一撫で、散らかっていれば撫でずに閉じる。言葉で聞かず行為で答えさせる。確認と掃除が同じ操作になりUIが1つ減る
- **B. 確認結果を蓄積して見せる。** 「机まわりは平均2日で散らかる」といった、確認からしか得られない情報を返す。統計画面は作らず1行だけ
- **C. 予測が外れたら halfLife が自動調整される。** 汚れ度が高いのに「綺麗だった」が続く区画は `halfLife` が伸びる。逆も然り

**C は Phase 1 の範囲外。** 学習には確認結果の履歴が要り、[domain-model.md](domain-model.md) の「永続化対象は Room と Area のみ」を変更することになる。また学習には初期値が必要なので、`halfLife` の初期値を決める作業自体は消えない。

## 3. 非目標

| やらないこと | 理由 |
|---|---|
| **バックエンド / クラウド同期** | このアプリに必要な理由がない。「なぜサーバを立てたか」に答えられない技術選定はしない |
| アカウント / 認証 | 同上 |
| リモートプッシュ（APNs） | ローカル通知で要件を満たせる（§5.1） |
| 家族・同居人との分担 | 既存アプリの領域。単身ワンルームに絞ることが差分 |
| 間取りの自由編集 | ポリゴン編集・吸着・undo は工数が読めない。将来もプリセット追加で対応 |
| 写真によるビフォーアフター | 別コンセプト。混ぜると焦点がぼける |
| 統計・グラフ画面 | §2.3-B のように1行で出すに留める |
| アイソメトリック表示 | 3Dへの中間形態。座標変換とタップ判定のコストに対し、Phase 2 で本物の3Dが来るため見合わない |

**バックエンドについて。** オフラインファーストで完成した既存アプリに同期を後付けするほうが、最初からサーバありきで設計するより難しく、話として面白い。要求が出るまで作らないが、Repository の protocol だけ切って実装を足せば対応できる状態にはしておく。

## 4. 画面

**全3画面。**

### 4.1 オンボーディング（2ステップ・初回のみ）

**Step 1 — 記録する場所を選ぶ**

区画チップを全オン状態で提示。オフにもできる。間取りが1つの現状では実質確認画面だが、`matchedGeometryEffect` の遷移元として必要で、将来間取りが増えた時にそのまま使える。

**Step 2 — 最後に掃除したのはいつ？**

「今日 / 数日前 / 覚えてない」の3択。初期 `lastVerifiedCleanAt` を決める。この設問がないと初回がピカピカから始まり現実と乖離する。「覚えてない」を置くこと自体が §2 の表明。

**遷移演出（見せ場）**

Step 2 完了後、チップが部屋の絵に組み上がる。`matchedGeometryEffect`。「これが自分の部屋だ」を作る最重要ポイント。完了後、通知許可を要求。

**掃除の頻度は聞かない。** 区画ごとに頻度を尋ねると5回の判断が増え、20秒が2分になる。これは §1.1 で批判した既存アプリのセットアップそのもの。また習慣がない状態で「風呂をどれくらいの頻度で掃除しますか」に正直に答えると「してない」であり、適当な数字は希望であって実態ではない。ペース調整は設定画面に置き、1週間使ってから触らせる（§4.3）。

作らない: スキップ、戻る、進捗インジケータ、間取り選択。

### 4.2 部屋（メイン）

アプリの中心。作業時間の半分をここに使う。

```
┌─────────────────────┐
│                     │
│    [ 部屋の描画 ]    │
│                     │
├─────────────────────┤
│ 机まわり、片付いてる？│  ← 1日1問
│   [ うん ]  [ いや ] │
└─────────────────────┘
```

「いや」を選ぶと、その区画の microTasks から1つが提示される。

**下段の問いは1日の途中で入れ替わらない。** 「その日の 0:00 時点で最も汚れていた区画」と定義することで、日中に掃除しても問いが変わらない（[domain-model.md](domain-model.md) の `dailyQuestion`）。

#### 描画

**平面図（真上から）。**

- 汚れ度に応じて色が変わる。**区画内は単色。** 空間方向のグラデーションはやらない（区画の境界が滲み、どこをタップすればいいか分からなくなる）
- 汚れの粒子を撒く。シードは区画IDで固定する（しないと再描画のたびに粒が踊る）
- 開いている間もじわじわ変化する

**配色**

明度だけでなく**色温度も動かす**。両方グレーにすると明度差だけになり変化が地味。clean 側を暖色寄りにすると dirty のグレーが冷たく見え、掃除した瞬間に「温度が戻る」感覚が出る。

| | 色 |
|---|---|
| clean | 生成り `#F5F2EB` 相当 |
| dirty | 冷たいグレー `#8C8C91` 相当 |

彩度も落とす。同じ色を暗くするだけだと「影」に見えるが、彩度を落とすと「くすみ」になる。ダークモードは別途2色を用意する（未決）。

#### 掃除アニメーション（今回の山場）

**モップで磨く表現。** 波紋やフェードより「掃除した」という身体感覚に近い。

`Path.trimmedPath(from:to:)` を使う。蛇行するパスを1本作り、progress 0→1 で部分的に切り出す。それを太くストロークしたものをクリップ形状として使い、汚れレイヤーをその外側だけに描く。粒子も同じレイヤーに描けば、モップが通った場所から一緒に消える。

実装時の注意:

- **方向は区画の長辺に沿わせる。** 縦長の区画を横に往復すると不自然。縦横比から自動で決められる
- **縁を柔らかく。** 境界がくっきり出ると「消しゴムで消した」感じになる。透明度の低いストロークをもう一回り太く重ねると湿った跡らしくなる
- **1.2〜1.6秒。** 往復するため波紋より長めが要る。ただし長すぎると連続操作でイライラする。実機で調整
- **モップの頭は出さない（まず）。** パス先端に矩形を置くと何が動いているか明確になるが、絵柄が具体的になる。物足りなければ後で足す
- **触覚は開始と完了の2回。** 往復ごとに鳴らすとうるさい
- `trimmedPath` + `strokedPath` を毎フレーム評価する。実機で 60fps に乗らなければ、パスを事前に分割して段階的に描く方式に切り替える

**完了条件: 汚れた部屋を操作すると気持ちよく綺麗になる。** これが達成できなければ他が全部できていても失敗。

作らない: 長押しメニュー、区画詳細画面、家具イラスト、履歴、統計、スクロール。

### 4.3 設定

- 通知オン/オフ
- 通知時刻（デフォルト 8:00）
- **ペース: [ こまめに ] [ ふつう ] [ ゆるめ ]** — `Tuning.paceMultiplier` を 0.7 / 1.0 / 1.5 に切り替え、全区画の `halfLife` に係数を掛ける。区画ごとの相対的な速さは定数のまま維持される
- 部屋のリセット（開発中の自分のためにも必要）

作らない: 区画編集、テーマ、区画ごとの速度調整、エクスポート、About。

## 5. 通知

### 5.1 方式: ローカル通知のみ

閾値到達時刻を事前に確定できるため、サーバ不要。根拠は [architecture.md](architecture.md)。

**スケジューリング戦略**

保留中通知は iOS の上限が64件。**3日分をまとめて予約する**（`Tuning` の定数）。確認・掃除のたびに全消去 → 再計算 → 積み直す。

1件だけ予約する方式は採らない。**アプリを開かない限り次が積まれず、1通で止まる**ため。継続できない人間が対象である以上、開かない日が続くことが前提になる。

事前予約でも**予測は外れない**。`lastVerifiedCleanAt` が変わる経路はアプリ内の操作だけなので、開かなければ予測は正確で、開けば積み直される。

**1日1通まで。** 区画ごとに送ると5区画で1日5通になり即オフにされる。

**時刻はデフォルト 8:00。** 起床直後は目覚ましと混ざって「うるさいもの」に分類されるため避ける。支度が一段落する時間帯を狙う。

**最初の7日間は特別扱い。** 汚れ閾値ベースだと初日に全部確認した後、数日通知が来ない。しかし習慣化に最も重要なのはその数日。`Room.createdAt` から7日間は、汚れ度に関係なく毎朝1通、確認を促す。8日目以降は通常モードへ。この分岐は通知を生成する同じ純粋関数の中で行い、別機構にしない。

**通知はメイン画面への導線でしかない。** 専用画面を持たない。タップするとアプリが開き、下段に同じ確認が出ている。

### 5.2 許可要求

**起動直後には出さない。** iOS は一度拒否されると再要求できず、設定アプリへ誘導するしかない。

オンボーディング完了 → 部屋が組み上がる演出 → 何のための通知か1行説明 → 要求。`UNAuthorizationStatus` で分岐し、拒否済みなら設定画面への導線を出す。

### 5.3 文面の原則

| 原則 | 良い例 | 悪い例 |
|---|---|---|
| 主語を部屋側に | 机まわり、どう？ | 掃除してください |
| 経過を責めない | しばらく経ちました | 3日サボっています |
| 量を小さく見せる | コップを1つ片付けませんか | 机まわりを掃除しましょう |

朝は時間がない。1度でも「無理だった」が起きると以降無視される。**通知から入る導線は、確認1タップで完結できること。**

**本文は予約時に固定される。** 配信時に差し替えられないため、区画名を含む文面は「3日分を予約する時点で、各日にどの区画が最も汚れているか」を計算して埋め込む。
